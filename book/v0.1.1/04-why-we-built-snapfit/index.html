Part 2: Snapfit · , Chapter 4

Why we built Snapfit

Let's take stock of where we are. Our services from Chapter 3 are written the right way: each one receives what it needs. What we want now is a composition root that works out the order by itself, shares every component, refuses mistakes when the program compiles, and shows the whole graph to anyone who reads it.

That is what we built snapfit for. Instead of writing the composition root, you declare it, and a macro writes it for you.

What the macro writes for us

#[container] reads the struct and writes the code we wrote by hand in AppState. Here is what it does, step by step:

  1. It writes the composition root. It generates ShopContainer::new(), which calls each component's constructor once, passing it clones of the fields listed in its deps. It also generates one get_<field>() method per field, so you can ask for any component.
  2. It works out the order. new() builds every field after the fields it needs. You never order the lines yourself, so when Database needs something new, you add one name to one deps list.
  3. It shares everything it builds. Every field is built once, and its getter hands you a clone of it. For an Arc field, every clone points to the same value, which is why the program printed true. No component is quietly built again on each call.
  4. It checks the graph when the program compiles. A name in deps that isn't a field, or two fields that need each other, stop the build with an error at the field. Chapter 12 shows each one.
  5. It names components by field, not by type. deps = [stock, payments] names fields, so two fields of the same type, such as a read replica and a primary database, are two different components (Chapter 9). When both go to the same constructor, a factory or a builder hands them over by name (Chapter 10).
  6. It leaves the services alone. OrderService asks for any Arc<dyn PaymentGateway>. Only the container says Stripe, by declaring payments as Arc<StripeGateway>, and Rust converts it when new() passes it in (Chapter 11). To switch providers, you change that field to another type that implements PaymentGateway and has a connect constructor taking the configuration. That is the whole change.
  7. It writes plain Rust. new() is the code you would have written in AppState::build, and a getter is a field access and a clone. Nothing is looked up while the program runs.

Why not build it by hand, or use a locator?

Here is how the three shapes we have seen compare:

Question Building by hand Service locator snapfit
Where is the graph? Spread over the constructor calls in build In the register calls, while the program runs In one struct
Who orders construction? You You, as you build what you register new(), worked out when compiling
When is a missing dependency found? When compiling When the program asks for it When compiling
Two components of one type? Yes, two variables No, one entry per type Yes, two fields
What does a lookup cost? A field access A hash lookup and a downcast A field access and a clone
Does the domain code change? No Only if services use the locator No

Which problem this solves

Every problem we found in Part 1, and the chapter where you can see how snapfit answers it:

Problem How snapfit answers it Where
Tight coupling Services receive their dependencies; only the container names an implementation. Chapter 6, Chapter 11
Hard to test A service is a plain struct: a test builds it with new(...) and fakes, without any container. Chapter 6
Duplicated resources Every field is built once; for an Arc field, every getter call returns the same value. Chapter 5
Mixed responsibilities A service knows only its own arguments; the container knows how everything is built. Chapter 7
A closed list A new implementation is a new type named in one field; no service changes. Chapter 11
Spreading type parameters The concrete type is named once, in a field's type, and services can take a trait object instead. Chapter 11
Someone still has to choose The container chooses, once, in the types of its fields. Chapter 11
Ordering by hand new() works out the order from deps. Chapter 8
Sharing by convention There is one kind of field: built once, when the container is built. Chapter 5
An invisible graph The container struct is the graph, in one place. Chapter 8
Arguments by position A factory receives its dependencies by name, and a builder takes them through setters named after them. Chapter 10
Run-time failures Unknown names and cycles are compile errors. Chapter 12
One entry per type Components are named by field. Chapter 9
Hidden dependencies Services never see the container, so they can't ask it for anything; each constructor lists what its service needs. Chapter 6, Chapter 13

Remember

  1. snapfit is dependency injection where the composition root is a struct you write and a macro completes.
  2. Services stay plain Rust: no attribute, trait or import of snapfit in them.
  3. The container is the only place that names implementations, orders construction and shares components, and the compiler checks it.
