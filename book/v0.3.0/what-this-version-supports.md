# What this version supports

This edition of **The Snapfit Book** covers the **`0.3`** releases of `snapfit`. It needs Rust **`1.85.0`** or newer, and your own crate can use any edition from 2018 on.

## Who 0.3 is for

`0.3` fits small and medium applications whose components can be built synchronously when the program starts, even when building one can fail: command-line tools, background workers, and web services whose clients and connection pools are created without waiting, such as an HTTP client or a database pool that connects lazily. It does one thing, and does it well: it builds a graph of shared components from one struct, and checks that graph while the program compiles.

## What it does

| Capability                                       | Details                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| :----------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Plain domain types**                           | Services, repositories and controllers need no attribute, trait or import of `snapfit` ([Chapter 6](https://marlon-sousa.github.io/snapfit-rs/book/v0.3.0/06-pure-domain-types.md)); a trait dispatched statically carries one attribute ([Chapter 13](https://marlon-sousa.github.io/snapfit-rs/book/v0.3.0/13-static-dispatch.md)).                                                                                                                                         |
| **Shared components**                            | Every field of a `#[container]` is built once, and its getter returns a clone of it, which for an `Arc<T>` field is the same value; fields can be `Arc<T>`, wrapped for you, or any `T: Clone` ([Chapter 5](https://marlon-sousa.github.io/snapfit-rs/book/v0.3.0/05-installing-and-first-singleton.md), [Chapter 7](https://marlon-sousa.github.io/snapfit-rs/book/v0.3.0/07-wiring-dependencies-and-constructors.md)).                                                      |
| **Dependencies by name**                         | `deps = [...]` lists the fields a component needs, passed to its constructor in that order ([Chapter 7](https://marlon-sousa.github.io/snapfit-rs/book/v0.3.0/07-wiring-dependencies-and-constructors.md)), or by name to a factory or a builder ([Chapter 10](https://marlon-sousa.github.io/snapfit-rs/book/v0.3.0/10-passing-dependencies-by-name.md)).                                                                                                                    |
| **Ways to build a field**                        | `new` by default, `build = default`, `build = constructor(<fn>)`, and `leaf_build = default` for a whole container ([Chapter 7](https://marlon-sousa.github.io/snapfit-rs/book/v0.3.0/07-wiring-dependencies-and-constructors.md)); `build = factory` and `build = builder` ([Chapter 10](https://marlon-sousa.github.io/snapfit-rs/book/v0.3.0/10-passing-dependencies-by-name.md)).                                                                                         |
| **Construction order worked out when compiling** | Fields can be declared in any order; each is built after the fields it needs ([Chapter 8](https://marlon-sousa.github.io/snapfit-rs/book/v0.3.0/08-read-the-container-know-the-graph.md)).                                                                                                                                                                                                                                                                                    |
| **Several components of one type**               | Fields are told apart by name, without wrapper types ([Chapter 9](https://marlon-sousa.github.io/snapfit-rs/book/v0.3.0/09-multiple-instances-of-the-same-type.md)).                                                                                                                                                                                                                                                                                                          |
| **Choosing an implementation**                   | A field's concrete type is the choice; or the field is a trait object, built from the type its `implementation` names, or by a factory that chooses while the program starts. Services take a trait object ([Chapter 11](https://marlon-sousa.github.io/snapfit-rs/book/v0.3.0/11-choosing-an-implementation.md)).                                                                                                                                                            |
| **Static dispatch**                              | `#[snapfit::static_dispatch]` on a trait of your own, and `static_dispatch_for` on the container, give one type for a closed list of implementations, whose calls are a `match` the compiler can inline; test stand-ins join the list under `cfg_attr(test, ...)` ([Chapter 13](https://marlon-sousa.github.io/snapfit-rs/book/v0.3.0/13-static-dispatch.md), [Chapter 14](https://marlon-sousa.github.io/snapfit-rs/book/v0.3.0/14-choosing-static-or-dynamic-dispatch.md)). |
| **Components that can fail**                     | A field marked `fallible = true` is built by a constructor, builder or factory that returns a `Result`; the container is built by `try_new()`, which returns the first failure as a `BuildError` naming its field ([Chapter 15](https://marlon-sousa.github.io/snapfit-rs/book/v0.3.0/15-when-building-can-fail.md)).                                                                                                                                                         |
| **Mistakes refused when compiling**              | Unknown dependencies and cycles, every one in the same build, each at its field ([Chapter 16](https://marlon-sousa.github.io/snapfit-rs/book/v0.3.0/16-mistakes-caught-by-the-compiler.md)).                                                                                                                                                                                                                                                                                  |

## What it doesn't do

If you have used dependency injection before, some questions probably came to mind while reading. Here are the ones that usually come first, and how `0.3` answers them:

1. **Can a constructor wait for something?** No. Constructors are synchronous, so a client that has to be awaited before it is usable can't be a field of the container.
2. **Can I pass values in?** No. `new()` takes no arguments. A configuration component reads its own settings, for example from environment variables, in its constructor.
3. **Can a field be a trait object without writing code?** Yes, when it is an `Arc` of one. A field typed `Arc<dyn PaymentGateway>` names the type to build with `implementation = StripeGateway`. Any other trait object, such as a `Box<dyn PaymentGateway>`, and a choice made while the program starts, are built in a factory ([Chapter 11](https://marlon-sousa.github.io/snapfit-rs/book/v0.3.0/11-choosing-an-implementation.md)).
4. **Can a trait of another crate be dispatched statically?** No. Only a trait of your own crate can carry `#[snapfit::static_dispatch]`, and a trait with a supertrait of another crate, such as `Display`, can't be dispatched statically either. Such traits are dispatched dynamically, as trait objects ([Chapter 14](https://marlon-sousa.github.io/snapfit-rs/book/v0.3.0/14-choosing-static-or-dynamic-dispatch.md)).
5. **Can a field give me a new value each time?** No. Every component is shared.
6. **Can a test replace one field of a container?** No. A test that needs different components declares its own container ([Chapter 11](https://marlon-sousa.github.io/snapfit-rs/book/v0.3.0/11-choosing-an-implementation.md), [Chapter 12](https://marlon-sousa.github.io/snapfit-rs/book/v0.3.0/12-testing-a-service-on-its-own.md)). A test of one service builds that service directly, with stand-ins for what it asks for ([Chapter 12](https://marlon-sousa.github.io/snapfit-rs/book/v0.3.0/12-testing-a-service-on-its-own.md)).
7. **Can a container be generic?** No. `struct ShopContainer<T>` is refused.

Some of these may come in later versions. We plan small, frequent releases rather than one large one, because `0.3` is already useful as it is. We don't promise what each release will hold, or when.
