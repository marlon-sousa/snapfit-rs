Pure domain types, one container

Our shop needs to bill its customers, which means adding tax to every order. Let's write the billing code, and see how the same struct can be tested on its own and wired into a container, without changing a line of it.

This is the lamp with a plug from Chapter 1. The same lamp works in the living room socket and on the test bench, because it doesn't care where the electricity comes from.

Why this matters

  1. No framework in your domain code. If your domain types live in a separate crate, that crate doesn't even list snapfit in its Cargo.toml. There is one exception, which we'll meet in Chapter 13: a trait you choose to dispatch statically carries one snapfit attribute, where it is defined. The types that implement it still don't.
  2. Tests build what they need. InvoiceCalculator::new is an ordinary function, so a test passes it any configuration it likes, with no container and no setup.
  3. The container is only for wiring. When BillingContainer::new() runs, it calls PricingConfig::new(), wraps the result in an Arc, and passes a clone to InvoiceCalculator::new(...). That's exactly what you would write by hand.

Which problem this solves

  1. Hard to test (Chapter 1): the calculator is built directly, as a unit test builds it, with its own configuration, without a container and without any real infrastructure.
  2. Tight coupling (Chapter 1): InvoiceCalculator::new receives its configuration. Whether that is the production configuration or a test's is decided by whoever calls it.
  3. Hidden dependencies (Chapter 3): nothing in InvoiceCalculator refers to the container, so it can't ask the container for anything. Its constructor says everything it needs.

Remember

  1. A domain struct wired by snapfit looks exactly like one written without it.
  2. A unit test of one service calls Service::new(...) directly, without building the container.
  3. Without build, #[singleton] calls <Type>::new(...).
