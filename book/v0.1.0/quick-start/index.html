What you just saw

  1. Plain domain structs. ShopConfig, CatalogDb and OrderCheckout don't import snapfit or implement any of its traits (Chapter 6).
  2. A component that needs nothing. config: Arc<ShopConfig> has no deps, so ShopContainer::new() calls ShopConfig::new() once and wraps it in an Arc (Chapter 5).
  3. Components that need others. db lists config, so it receives a clone of it in CatalogDb::new(...); checkout lists db and is built after it (Chapter 7).
  4. One of each. Each component is built once, and get_checkout() returns a clone of the same Arc<OrderCheckout> every time (Chapter 5).

Which problem this solves

Part 1 walks through the problems of wiring an application without snapfit, and Chapter 4 shows where each one is answered. On this page you met two of them:

  1. Tight coupling (Chapter 1): OrderCheckout receives its database; only ShopContainer decides what it is.
  2. Ordering by hand (Chapter 3): nobody orders the construction. ShopContainer::new() builds each field after the fields its deps lists.

Remember

  1. Domain structs stay plain Rust; only the container carries snapfit attributes.
  2. Every #[singleton] is built once, after the fields it needs, and its get_<name>() returns a clone of it.
